# Structural Certificate Draft Export Plan

**Goal:** Add an auditable export workflow that turns an exact saved Structural
Workbench result into a controlled, unsigned structural certificate draft and
complete engineering-review pack without implying that Tertius itself has
issued or signed an engineering certificate.

**Document type:** Implementation plan

**Plan date:** 2026-09-03

**Status:** Implemented; automated and live deployment validation recorded below

## Product decision

Tertius will export a **controlled structural certificate draft** for review and
signature by an appropriately qualified engineer. It will not call an unsigned
file an issued certificate, apply an engineer's signature, or claim acceptance
by a council, certifier, or other appropriate authority.

The first release will provide two related downloads:

1. `*-structural-certificate-draft.pdf` — a human-readable controlled draft
   containing the decision, scope, governing results, conditions, applicability
   schedule, evidence register, and blank engineer declaration/signature block.
2. `*-structural-review-pack.zip` — the same PDF, the complete authoritative
   structural evidence JSON, and a manifest containing the file hashes and the
   exact analysis identity.

The existing client-generated engineering-review JSON remains available during
migration, but the review-pack JSON must be generated by the server from the
saved result so it cannot diverge from the PDF.

## Current baseline

- `StructuralAnalysisResult` already persists the exact structural snapshot,
  design digest, configuration digest, site digest, engine version, selected
  combination key, calculation duration, and creation time.
- `StructuralWorkbench.tsx` already downloads a useful but incomplete
  client-assembled evidence JSON.
- `site_wind_report.py` already proves that authenticated, server-side `fpdf2`
  reports work in this runtime.
- `CertificationReadiness` currently says `certificate_ready` and
  `ready_for_certificate`, although the product has no certificate document or
  engineer-signing workflow.
- Serviceability currently reports 101 passing checks and 22 `not_checked`
  rows for the demo shed. All 22 are axial-only braces/ties for which transverse
  `L/n` beam deflection is not applicable; axial deformation, member resistance,
  connections, and bracing load path are checked elsewhere.
- The serviceability stage currently ignores every `not_checked` row once at
  least one applicable check has run. That is too broad for certificate export:
  a genuine missing criterion must block, while a proven non-applicable check
  must be disclosed but must not block.

## Non-negotiable rules

- Build every report from one exact persisted `StructuralAnalysisResult`. Never
  accept a structural snapshot, readiness flag, pass count, or calculation data
  from the browser.
- The report request must name the analysis cache key that the user reviewed.
  Reject the request if that key is no longer the active project's current
  design/configuration/site/engine identity.
- Exporting must not re-run the structural solver. A certificate draft is a
  rendering of saved evidence, not a new analysis pathway.
- A failed, unsupported, blocked, stale, or genuinely `not_checked` item blocks
  certificate-draft creation. Only explicitly `not_applicable` checks with a
  recorded reason may be excluded from a gate.
- Show non-applicable checks in the document; do not silently omit them or hide
  them behind a generic disclaimer.
- Put `CONTROLLED DRAFT — ENGINEER REVIEW AND SIGNATURE REQUIRED` on the cover
  and every page. Leave engineer name, qualifications, registration, signature,
  and date blank.
- Do not derive `ready_for_order` from technical calculation readiness. Ordering
  and certificate issuance require a separate, explicit product policy and are
  outside this implementation.
- Preserve tenant/project isolation in both application queries and database
  constraints. Do not put raw user, tenant, project, analysis, or report IDs in
  metrics or logs.
- Do not fetch remote content while building the PDF. Treat project names,
  labels, assumptions, references, and URLs as untrusted display text and bound
  their length before rendering.
- Follow NCC Part A5 evidence principles: identify the subject and basis, state
  conditions and limitations, retain complete evidence, and make the document's
  status unambiguous. Authority acceptance remains outside Tertius.

## User workflow

```text
Open Structural Workbench
  -> load exact saved governing analysis
  -> technical gates pass and no genuine open checks
  -> click "Download certificate draft"
  -> server revalidates active analysis identity and readiness
  -> server creates or reuses immutable report export
  -> browser downloads controlled draft PDF
  -> optional "Download full review pack" downloads PDF + JSON + manifest
  -> engineer reviews, amends outside Tertius if required, and signs externally
```

If the design, Site basis, structural configuration, or engine changes after the
Workbench result was loaded, export must return a stale-result conflict and tell
the user to reopen Structural and review the new calculation.

## Document structure

### Part A — Controlled certificate draft

1. **Cover and document control**
   - Project name and site address.
   - Document title and conspicuous unsigned-draft status.
   - Tertius report identity, report schema version, analysis time, report time,
     and page numbering.
   - Design, structural configuration, Site, engine, analysis-cache, and evidence
     digests using readable prefixes plus complete values in the evidence
     register.
2. **Proposed engineering statement**
   - The exact design revision assessed.
   - NCC classification, importance level, design life, jurisdiction, compliance
     pathway, and standards register.
   - A restrained statement that the listed technical gates passed in the saved
     analysis and that engineer review/signature is still required.
3. **Scope and conditions**
   - Structural system included in the analysis.
   - Loads and combinations considered.
   - Material, product, fabrication, fastener, support, erection, and maintenance
     assumptions on which the result relies.
   - Explicit exclusions and matters requiring site/installation confirmation.
4. **Engineer declaration**
   - Blank fields for name, qualifications, registration number/jurisdiction,
     organisation, signature, date, and any engineer-added conditions.
   - No pre-filled identity and no electronic signature in this release.

### Part B — Engineering calculation report

1. Project, Site and wind-action basis.
2. Model summary: member/node/support counts, dimensional envelope, solver and
   stability method, governing combinations, and equilibrium result.
3. Eight Australian readiness gates with status, reference, and summary.
4. Governing ULS member cross-section and member-stability results, grouped by
   physical member rather than solver fragment.
5. Governing connection, anchor, tension-member, restraint and bracing-load-path
   results.
6. Serviceability summary for every applicable physical member.
7. Global stability/P-Delta convergence and applicability evidence.
8. Calculation-sheet register with standards, pack/version identifiers, source
   references, related member IDs, and full evidence JSON location/hash.

### Annex A — Applicability, exclusions and limitations

- List every `not_applicable` item with physical member ID, analytical member
  IDs, excluded test, reason, and the verification family that covers the actual
  behaviour.
- For the current demo shed, group and list the 8 `LWB*`, 6 `GEB*`, and 8 `RPB*`
  axial brace/tie members. Use wording equivalent to:

  > Transverse span-deflection criteria are not applicable to these axial-only
  > bracing members. Axial deformation and resistance, end connections, and the
  > bracing load path are verified in the referenced calculation stages.

- Distinguish `not_applicable` from limitations of the study. The former is a
  reasoned applicability decision; the latter describes the boundary conditions
  and assumptions on which the complete design assessment relies.
- A positive certificate draft must contain zero generic `not_checked`,
  `unsupported`, `blocked`, `stale`, or failed items.

## Authenticated API

**Files:**

- Modify: `server/workflows/structural/structural_server.py`
- Create or modify: `server/tests/structural/test_certificate_export_api.py`

Add body-keyed active-project endpoints so raw identifiers are not placed in
access-log URLs:

- `POST /api/structural/active/report/certificate-draft.pdf`
- `POST /api/structural/active/report/review-pack.zip`

Request body:

```json
{
  "analysis_key_digest": "the full cache key shown by the reviewed workbench"
}
```

Server flow:

1. Resolve the authenticated user's active project within their tenant.
2. Rebuild the current structural analysis identity from the current compiled
   capture, configuration and Site definition without solving it.
3. Require exact equality with the requested key and load that persisted result.
4. Validate the stored snapshot against the current contract.
5. Require `ready_for_certificate_draft`, all required gates passing, complete
   model coverage, zero open issues, zero genuine unchecked/unsupported/failed
   checks, and reasoned `not_applicable` rows.
6. Create or reuse the immutable report export.
7. Return the requested bytes with private/no-store caching, safe content type,
   sanitized filename, report-identity header, artifact SHA-256 header, and
   `X-Content-Type-Options: nosniff`.

Failure behaviour:

- `404`: no active project or no saved result.
- `409`: browser-reviewed analysis key is stale relative to current inputs.
- `422`: analysis exists but certificate-draft prerequisites are not satisfied;
  return bounded gate/check summaries and next action, not the full snapshot.
- `500`: deterministic rendering/persistence error; never return a partial PDF.

- [ ] Add a request timeout and response-size guard without using the compile-job
  queue; report generation should be seconds and must not start a CAD compile or
  structural solve.
- [ ] Record only bounded telemetry such as outcome, document kind, cache
  reuse/new, generation duration, and byte-size bucket.

## Rollout sequence

1. Land applicability semantics and gate tests first. Do not build certificate
   export on the ambiguous `not_checked` behaviour.
2. Land the report contract, persistence migration, deterministic renderer and
   API behind tests.
3. Land the Structural UI actions and updated wording.
4. Validate a locally generated demo-shed PDF visually before deployment.
5. Deploy matched API/UI images to isolated k3s smoke and run authenticated
   end-to-end validation.
6. Deploy to the demo DNS only after the exact report identity, counts, hashes,
   stale-result rejection and re-download behaviour are proven.

## Explicitly out of scope

- Applying or storing an engineer's digital signature.
- Verifying professional registration or jurisdictional authority.
- Allocating an authority/council certificate number.
- Submission to a certifier, council, planning portal, or document-management
  system.
- Treating technical readiness as construction approval or permission to order.
- Allowing a user to edit calculated values or suppress checks inside the report.

Those require a separately designed signing/issuance workflow with roles,
identity assurance, amendment/revocation handling, and jurisdiction-specific
legal review.

## Definition of done

- The demo shed shows `101 pass`, `22 not applicable`, `0 fail`, and
  `0 not checked` for serviceability.
- The workbench exports a controlled PDF draft and complete review pack from the
  exact saved analysis without recomputing it.
- Every downloaded artifact is immutable, tenant-scoped, reproducible, hashed,
  and traceable to design/configuration/Site/engine identities.
- Any stale input or genuine open check blocks the positive draft with a useful
  next action.
- The PDF exposes scope, conditions, limitations, non-applicable checks and the
  evidence chain, and remains visibly unsigned on every page.
- An engineer can review the pack and sign externally without needing the live
  browser session to understand what was assessed.

## Regulatory references used for document design

- [NCC 2022 Volume Two, Part A5 — Documentation of design and construction](https://ncc.abcb.gov.au/editions/ncc-2022/adopted/volume-two/a-governing-requirements/part-a5-documentation-design-and-construction)
- [ABCB Evidence of suitability handbook](https://ncc.abcb.gov.au/resource/handbook/evidence-suitability-handbook)

These references guide evidence structure and disclosure only. The reviewing
engineer and appropriate authority determine whether the final signed evidence
is sufficient for the particular project and approval pathway.
